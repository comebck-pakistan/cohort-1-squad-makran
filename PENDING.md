## Improvements in agent loop

Real flaws found live during the Agent-run E2E pass (2026-08-05), and how each was resolved. Kept as its own section since these are behavior changes to the core loop, not just test coverage.

- **"Repo needs at least one commit" was a missing feature, not a real limitation.** Root cause: `ensureBranch`/`getRefSha` (`lib/github.ts`) assumes the connected repo already has a default-branch ref; a genuinely empty repo 409s `"Git Repository is empty."`. Fixed two ways. (1) Solvo now creates the repo itself for any meeting with a known client: `lib/github.ts`'s new `createGithubRepo()` calls `POST /user/repos` with `private: true, auto_init: true`, the `auto_init` is what eliminates the empty-repo condition at the source (GitHub commits a README synchronously at creation). `lib/actions/client-repos.ts`'s new `ensureClientRepo()` reuses an existing repo for repeat meetings with the same client (one repo per client, `repos.client_id`, new column) instead of creating one every time, calls it from `promoteDraftTickets` (`lib/actions/meetings.ts`) whenever a meeting has a known client, and fires a `"repo-created"` notification (in-app + email) the first time. Manual repo choice is kept only for the one case that's genuinely irreducible, a meeting with no identified client. (2) For the still-supported manually-connect-an-existing-repo path, `gh()` now specifically classifies the "Git Repository is empty" 409 as a clean `NonRetriableError` instead of an unclassified retriable `Error`, so it reaches `needs_human` immediately with an honest reason instead of burning through retries first.
- **`needs_human`/`failed` states didn't say why.** `agent-run.ts` and `ticketize.ts` already computed a specific reason string at every failure exit (`"CI failed at max attempts."`, `"No transcript available"`, etc.), it just never left the Inngest function's return value, nothing persisted or displayed it, so the UI only ever showed one generic message regardless of cause. Fixed: new `tickets.failure_reason` / `meetings.failure_reason` columns, written at every existing `needs_human`/`failed` transition (all 5 in `agent-run.ts`, both in `ticketize.ts`, including the `onFailure` crash handlers using `error.message`), surfaced on `TicketDetailScreen`'s "Agent stopped" card and as a tooltip on `MeetingsOverviewScreen`'s "Failed to process" pill.
- **Real bug caught mid-verification: `notifications_type_check` didn't know about the new type.** Adding `"repo-created"` to the TS `NotificationType` union without a matching migration meant the first real repo-creation notification insert 500'd on a Postgres CHECK constraint (`supabase/migrations/20260804020000_notifications.sql`'s `type in (...)` list). A real private repo was still created successfully on GitHub before the crash (confirmed via direct DB query, `repos` row + real `auto_init`'d GitHub repo both existed, just the notification never got written). Fixed with a follow-up migration extending the constraint; re-running the same confirm correctly reused the already-created repo (no duplicate) and the notification fired on a second, fresh client. A reminder that this codebase's "enum" columns are enforced by a Postgres CHECK, not just a TS union, both need updating together.
- **Add Meeting modal's client picker was decorative, now wired for real.** `clientQuery` state existed but was never used to resolve a `client_id`; both `scheduleBotMeeting` and `createManualMeeting` hardcoded `clientId: null`, and the "Paste transcript" mode didn't even render the field. Fixed: `AddMeetingModal` (`features/meetings/AddMeetingModal.tsx`) now takes the real `clients` list (already loaded by `MeetingsOverviewScreen`), filters client-side on the existing search input, shows a real dropdown of matches, and both submit paths now send the selected `clientId`. Also added the field to "Paste transcript" mode (it was bot-mode only before), and fixed a bug this exposed: `scheduleBotMeeting`'s `known_client` flag only ever looked at guest-email matching, so a client picked directly in the modal wouldn't have counted as "known" (would've skipped the auto bot-confirm send). Now `known_client` is true if either the guest email matched or a client was explicitly picked. Verified live: selected a real client in both modes, submitted a real manual-paste meeting, confirmed it landed on `/meetings` with the real client name (not "–") instead of unattached.
- **Human gate reduced: "Assign agent" click removed, no safety loss.** Audited all 4 human gates between transcript and merged work (confirm-tickets, assign-agent, plan-approval, PR-review/merge). Assign-agent carried zero decision content, it's a plain "go" click with nothing to review, and plan-approval sits immediately after it as the real first checkpoint (agent hasn't touched the repo yet at that point). The other 3 gates each gate a real decision (scope commitment, code-change intent, irreversible repo mutation) and stay manual. Fixed: `promoteDraftTickets` (`lib/actions/meetings.ts`) now creates tickets directly into `agent_running` and fires `ticket/state-changed` + `ticket/agent-assigned` itself, instead of leaving them in `backlog` for a separate click. Cuts 4 clicks/ticket to 3; `backlog` state is now unreached in the normal flow (left in place, harmless, `TicketsBoardScreen`'s column just stays empty).
